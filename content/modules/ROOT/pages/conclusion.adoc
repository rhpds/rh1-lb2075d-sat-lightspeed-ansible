== Next Steps

The pattern this lab demonstrates — detect, route, remediate, verify — applies beyond the specific CVEs used here. A few directions to take it further:

* *Widen the remediation scope.* The `vulnerability_remediation.py` script defaults to Critical and Important only. Pass additional `--severity` values in `find_and_remediate.yml` to include Moderate. A broader policy remediates more, but also touches more packages per run, so review the tradeoffs first.
* *Target specific CVEs.* The script supports a `--cve CVE-YYYY-NNNNN` argument to scope a single run to one CVE. Use this to write targeted remediations for zero-day CVEs as they land, without waiting for a full-fleet sweep.
* *Change the trigger event.* This lab fires on any successful remote execution job. Real deployments often trigger on a recurring schedule, a newly registered host, or a content view promotion. Satellite exposes dozens of webhook event types — browse them in *Administer -> Webhooks -> New Webhook* to find the one that fits your workflow.
* *Extend the EDA rulebook conditions.* The current rulebook fires on `condition: true`, meaning every webhook event triggers the Job Template. Add conditions to filter by host group, environment, or payload field before launching remediation, so the pipeline only acts when the event is actually relevant.
* *Report back to Satellite automatically.* Running `insights-client` by hand in Module 5 closed the gap between the live RPM database and Satellite's Vulnerability dashboard. A post-remediation task in `find_and_remediate.yml` can run `insights-client` on each patched host automatically, eliminating that manual step.
